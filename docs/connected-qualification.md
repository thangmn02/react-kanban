# Connected qualification and recovery

Local Docker acceptance and hosted Supabase acceptance are separate gates. The local tools below refuse to use hosted API URLs. No report or local PASS authorizes a production migration, user-record repair, release or installed-app replacement.

Production release preparation keeps operator credentials outside the OneDrive checkout at `%LOCALAPPDATA%/Kora/secrets/production.env`, protected for the current Windows user. `KORA_PRODUCTION_ENV_FILE` can explicitly select another private non-synced source. `.gitignore` is a Git exclusion, not a cloud-sync exclusion. Production inspection and backup preparation do not authorize production writes or deployment.

The private-image function reads `SUPABASE_SERVICE_ROLE_KEY` from Netlify's production **Functions** environment at runtime, alongside the public Supabase URL/client key. The local operator variable `KORA_PRODUCTION_SERVICE_ROLE_KEY` is not automatically imported or published. Never give it a `VITE_` prefix or include it in Tauri assets. Configuring the function environment or deploying it requires separate release authorization. A key restricted to this backend must not be reused for unrelated backup/admin routines.

`scripts/qualify-authorized-staging.mjs --production-read-only-backup` has an independently pinned production target and performs hosted reads plus isolated local recovery only. It refuses to download private production Storage objects with the backend key. `--database-only` can verify database recovery independently, but explicitly reports incomplete Storage recovery when objects exist; it is not a complete release backup. Keep production database archives encrypted outside the checkout. Storage byte recovery needs separate authorized backup access. Inspect the owning release plan before running any production preparation.

## Local Supabase

Use the existing `react-kanban` Docker stack from the repository's Supabase configuration. Do not reset an existing database to qualify a feature. Before schema or fixture-data changes, run:

```powershell
node scripts/qualify-local-supabase.mjs --output=scratch/my-qualification-backup
```

The output directory must be fresh: the full binary archive refuses overwrite. The tool snapshots table counts, takes a full PostgreSQL custom archive and restores public/auth/storage/app_private/migration schemas into a disposable database with original ownership and policies. It compares all table counts and drops only its generated restore database in `finally`. Its manifest explicitly excludes platform-extension recovery and Storage object bytes. Keep the archive private; a database dump contains account data. Object files and off-device recovery require separate backups.

Add `--apply` only for this local stack after reviewing pending repository migrations. The tool performs a fresh successful backup/restore first, then applies pending migrations and their Supabase history entries together in one transaction. A failed restore prevents source changes. It does not change hosted migration history. Recover only into a separately approved target; use the retained custom archive and restore commands in the tool after stopping writers, and restore Storage object bytes separately if needed.

Actual local integration commands are:

```powershell
node scripts/verify-local-connected.mjs
node scripts/qualify-local-supabase.mjs --output=scratch/integration-261027-0739/local-database-before-ui
node scripts/verify-connected-profile-browser.mjs
```

The current verification scripts use the private integration receipt directories shown in source; fresh reruns must retain or deliberately select a new backup/evidence directory. The connected service check requires its restore-verified backup receipt, provisions only generated test identities and exercises owner/admin/member/viewer/unrelated access through real Auth/PostgREST/Storage/Realtime. The UI check builds the actual connected frontend using local public client configuration, signs in through the actual form, edits/crops/uploads through Settings, verifies cancellation, reload/sign-in persistence and default-image retirement. Service-role credentials remain in memory for fixture provisioning/cleanup; they are never built into the app or printed. The UI runner owns loopback port 5174 and its dedicated browser/server, closing both in `finally`. Existing Docker containers belong to the user and are left running.

The task service subscribes to `public.tasks`. Clean baseline stacks previously published only briefing pins. The [task publication migration](../supabase/migrations/20261027010000_task_workflow_realtime.sql) adds tasks only if absent and fails if the Supabase publication is missing. It changes neither table grants nor RLS. Removing that publication membership is the narrow schema rollback; retain/reconcile changes received by clients before rolling back application code.

## Hosted staging checklist

1. Identify an explicitly authorized non-production project in the provider console. Record its owner/project identity independently of the currently linked ref. Do not infer staging from a name or an environment variable.
2. Inspect actual table/function/policy/publication metadata and `supabase_migrations.schema_migrations`. The authoritative hosted project's historical empty migration history must be reviewed before any repair or push. Do not push the squashed baseline blindly.
3. Back up the exact target with the existing [backup/restore tool](../scripts/backup-supabase.ps1) using an independently linked staging checkout and approved PostgreSQL tools, or the provider's approved recovery route. Prove restoration, record archive hashes, and separately cover object bytes and recovery credentials. A schema-only dump is insufficient.
4. Prepare migration order/hashes with `node scripts/qualify-staging-migrations.mjs`. Optional `--inspect --output=scratch/staging-metadata.json` requires `KORA_STAGING_PROJECT_REF`, matching direct `PGHOST`, PostgreSQL client credentials supplied through normal PG environment variables and trusted TLS roots. It uses `verify-full` and a read-only transaction. The tool refuses `--apply`.
5. Review dependencies against actual metadata: baseline, recurring-task schema, transactional task RPC, private identity image policies, then task publication membership. Use the approved Supabase migration process so successful migrations and version history agree. First inspect its dry run in a separate staging checkout; neither `migration repair` nor production push is authorized here.
6. With actual staging identities, repeat transactional completion/reopen/move, duplicate operation and recurrence tests; verify viewer/unrelated denial and owner/admin/member access. Verify invitation expiry/acceptance and role changes using the existing server RPCs/RLS.
7. Run authenticated Settings upload/cancel/default replacement, shared-workspace identity reads, unrelated/cross-owner denial, signed-URL expiry, account switching and reauthentication. Verify previous-image cleanup after a confirmed profile pointer and outage/retry behavior.
8. Verify realtime while connected, after disconnection and resubscription, and authoritative refresh after offline writes. Publication membership alone is not acceptance. Do not promote local service receipts to hosted acceptance.
9. Record exact source/build/migration identities and review recovery before a hosted operation. Do not auto-repair historical rows. Rollback the new function/policies/publication only from the recorded pre-change definitions after checking compatibility with active clients; retain image bytes/profile pointers and restore whole data only through the approved recovery procedure.

## Historical task reconciliation

Run `node scripts/audit-task-workflow.mjs private-snapshot.json`. Output includes each affected task ID, board/workspace/list identity, current completion state/position/timestamps, proposed operations, ambiguity and reversibility. It is a snapshot preview, not a live query. Never derive a historical completion time from `updated_at`, and never run a proposed complete operation automatically just to fill a timestamp. A reviewed repair must lock/compare current versions, retain complete before-images and positions, and have a verified backup.

## Notes collaboration boundary

Existing membership roles, assignment identities, invitation RPCs and workspace RLS remain the owners of collaboration. Connected Notes adds the [resource migration](../supabase/migrations/20261027020000_connected_notes.sql); its permission matrix and device-draft/import behavior are described in [task workflow](task-workflow.md). Content writes use explicit revision conflicts (`PT409`), request identities and actor-account fences. Do not use SQLSTATE `40001` for application revision conflicts: some PostgREST versions retry it as a serialization failure.

Real Notes service/browser checks use [qualification-target](../scripts/qualification-target.mjs) to admit only the backed-up local stack or the independently authorized staging project. They never select the production-linked ref. `verify-connected-notes.mjs` tests actual authenticated resource permissions and writes. `verify-connected-notes-browser.mjs` builds the selected connected frontend and tests sharing, revocation, deliberate transport outage, durable drafts, task-editor continuity, conversion and Trash/Restore. A deliberate outage aborts requests; it does not return fabricated successful data.

It stores full database archives outside the repository under `$USERPROFILE/.codex/backups/kora-staging`, with a private Windows ACL and DPAPI CurrentUser encryption. Recovery requires that Windows account/key context; this is not an off-device disaster-recovery claim. The saved encrypted archive is decrypted, hash-checked and restored with original owning schemas/ACLs in an isolated container without networking or host ports. The tool separately encrypts and restores existing Storage object bytes, verifies their SHA-256 hashes, and compares source row values, application object/policy/trigger/grant identities, provider RLS/ownership and publication membership. Schema privileges are restored with their original grantors because a schema-filtered `pg_restore` omits namespace ACL entries. Platform extension binaries and provider infrastructure remain provider recovery responsibilities.

Its transaction locks affected Auth/Storage parents, holds read locks on provider-owned tables, rechecks provider versions, and commits source migrations with their history. Provider tables do not receive broader grants. A failed or disconnected commit is reconciled read-only before retrying; a later verification failure never means an already committed transaction rolled back.

It compares current row values, object bytes, enforcement and publication state again under transaction locks. Run its `--check-hosted-transaction` rollback rehearsal first and require unchanged-state verification before the commit operation.
